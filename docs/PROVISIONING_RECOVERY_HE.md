# התאוששות בטוחה בתהליך Provisioning

## מטרה

למנוע יצירה כפולה כאשר בקשת יצירה ל־GitHub, Neon או Render התקבלה אצל הספק אך התשובה אבדה, או כאשר תהליך האשף נעצר בין יצירת המשאב לבין שמירת המזהה שלו.

## עקרונות

1. לפני POST ליצירת משאב נשמרת רשומת פעולה עם status=intent, ספק, שם משאב וסמן התאוששות אקראי בן 128 ביט.
2. סמן ההתאוששות נשמר במצב התהליך לפני כל פעולת כתיבה. הוא מזהה את ניסיון ההקמה, אינו סוד ואינו credential.
3. אם התהליך נעצר לאחר שמירת intent, ניסיון חוזר אינו שולח POST נוסף. הוא מבצע רק קריאות GET לאיתור משאב עם אותו סמן.
4. גם תשובת HTTP 2xx עם JSON תקין תחבירית אך במבנה חסר או בלתי צפוי, תשובת GET שאינה מאפשרת התאמה אמינה, או כשל באימות שירות לאחר שהספק אישר יצירה, נחשבים לתוצאה עמומה. אין לסמן אותם ככישלון רגיל שמאפשר POST נוסף.
5. משאב מאומץ רק לאחר התאמת הסמן וגם אימות owner/organization/workspace, region, source, branch, plan ו־CI לפי הספק.
6. כאשר לא ניתן להוכיח בעלות — התהליך נעצר במצב unknown. אין מחיקה אוטומטית ואין ניסיון יצירה נוסף.

## מיקום הסמן אצל כל ספק

| ספק | מיקום הסמן | בדיקת התאוששות |
|---|---|---|
| GitHub | Repository description: `Business application \| Business Studio provisioning:<32 hex>` | GET של Repository מדויק, `private=true` ו־description תואם |
| Neon | שם ענף ברירת־המחדל: main-bs-<12 hex> | GET של רשימת ענפי הפרויקט ואימות שהענף תואם ומסומן default |
| Render | משתנה סביבה לא־סודי BUSINESS_STUDIO_PROVISIONING_ID | GET של משתני הסביבה בשירות ואימות ערך מדויק, ואז אימות Free / Frankfurt / checksPass |

ה־Neon project שומר את שם הפרויקט העסקי; רק שם ענף ברירת־המחדל משתנה כדי לשאת סמן ייחודי. חיבור האפליקציה נלקח מברירת־המחדל של הפרויקט, ולא מסתמך על שם הענף.

## מצבי פעולה

- intent: הכוונה נשמרה לפני שליחת בקשת היצירה.
- unknown: תוצאת כתיבה אינה ידועה (timeout, תשובת 5xx או תשובת JSON פגומה).
- reconciling: ניסיון חוזר שמבצע קריאות GET בלבד.
- completed: מזהה המשאב נשמר ואומת.
- failed: התקבלה שגיאה ידועה שאינה מעידה על יצירה עמומה; לאחר תיקון ניתן לנסות שוב.

## מגבלות והתנהגות ידנית

ה־API-ים אינם מספקים טרנזקציה משותפת או מפתח idempotency אחיד לכל פעולות יצירת המשאבים. לכן המימוש אינו טוען ל־exactly-once. הוא משתמש בסמנים ספקיים ובמדיניות at-most-once:

- אם הסמן נמצא והמשאב תואם — האשף משחזר את המזהה וממשיך.
- אם הסמן אינו נמצא, אינו קריא או עדיין אינו גלוי — האשף עוצר ואינו שולח POST נוסף.
- אם קיים משאב באותו שם ללא סמן תואם — הוא אינו מאומץ לפי שם בלבד.
- אם נדרש טיפול ידני, המפתח בודק את תיאור ה־Repository, ענף ברירת־המחדל ב־Neon או משתנה הסביבה ב־Render. אין למחוק או לשנות משאב לפני אימות בעלות ונתונים. לאחר הבדיקה נדרשת פעולת התאוששות מפורשת; אין מסלול אוטומטי שמסמן משאב לא ידוע כ"לא נוצר".

## פרטיות וסודות

סמן ההתאוששות אינו מכיל סוד. מצב התהליך שומר מזהי משאבים, סטטוסי פעולה וסמן בלבד. מפתחות API, DATABASE_URL, סיסמת מנהל, SECRET_KEY וערכי סודות אחרים אינם נשמרים במצב או ביומן. משתנה Render BUSINESS_STUDIO_PROVISIONING_ID הוא מזהה correlation לא־סודי בלבד. בעת התאוששות משירות Render קיים, האשף אינו מייצר מחדש או דורס את `SECRET_KEY`, את `ADMIN_PASSWORD_HASH` או סודות אינטגרציה שכבר נוצרו; סבב סודות מכוון הוא פעולה נפרדת.

## בדיקות

בדיקות המימוש משתמשות ב־mocks ומכסות:
- timeout אחרי יצירת Repository, פרויקט Neon או שירות Render, ולאחריו התאוששות באמצעות סמן תואם;
- סמן חסר או משאב לא גלוי — ללא POST חוזר;
- מניעת אימוץ של משאב לא מזוהה;
- סיווג HTTP 5xx, JSON פגום/חסר ותשובת Repository לא תקינה כמצב כתיבה עמום;
- כשל בקריאת אימות Render לאחר יצירה — נשאר unknown ואינו שולח POST נוסף;
- סירוב להתאושש משירות Render שאינו Free, Frankfurt ו־CI-gated.

הבדיקות אינן יוצרות משאבי ענן אמיתיים ואינן מאמתות חיוב או זכאות Free אצל ספק.


## מניעת Execute מקביל (Atomic Workflow Claim)

כל הפעלת Execute רוכשת claim בלעדי לפי מזהה workflow לפני טעינת מצב התהליך או ביצוע Preflight/כתיבה. claim מוחזק לאורך כל ההקמה ומשתחרר בבלוק `finally` גם כאשר הפעולה נכשלת.

- כאשר `DATABASE_URL` מוגדר: נעשה שימוש ב־PostgreSQL session-level advisory lock עם `pg_try_advisory_lock(hashtextextended(workflow_id, 0))`. החיבור מוגדר `autocommit` כדי שלא יישאר idle transaction בזמן המתנה ל־API חיצוני. אם lock תפוס, Execute נוסף נדחה ללא שינוי מצב וללא קריאה לספק.
- במצב קובצי local: נרכש OS file lock על קובץ lock פרטי תחת תיקיית runs. נעילת מערכת ההפעלה משתחררת גם כאשר התהליך מסתיים באופן לא צפוי; קובץ ה־lock עצמו אינו מכיל נתוני לקוח או סוד.
- הנעילה היא לפי workflow_id; תהליכים עבור מזהים שונים אינם חוסמים זה את זה.
- הכשל ברכישת claim הוא fail-closed: לא מתבצע ניסיון לטעון או לשנות workflow, ולא נשלחות בקשות יצירה.
- PostgreSQL advisory lock הוא session-scoped ואינו מבטיח Exactly-Once מול ספקי ענן. הוא מונע שני Execute מקבילים באותו זמן; מנגנון create-intent וההתאוששות הספקית נשארים אחראים לתוצאות עמומות לאחר קריסה.

בדיקות regression מכסות claim מקומי בלעדי ושחרורו, וכן את מסלול advisory lock של PostgreSQL כולל busy-state ושחרור נעילה.


### Scope הנעילה: business slug

ה־claim של Execute חייב להשתמש ב־business slug יציב לפני `plan_id`. `plan_id` הוא מזהה של תוכנית/ניסיון תכנון ועלול להשתנות כאשר המפתח מפיק Dry Run חדש לאותו עסק. נעילה לפי `plan_id` בלבד הייתה מאפשרת לשתי תוכניות שונות לאותו slug לרוץ במקביל ולנסות ליצור אותם משאבים. לכן ה־slug משמש מפתח נעילה; `plan_id` נשאר מזהה התיעוד וההתאוששות של התוכנית עצמה. עסק חדש עם slug אחר אינו נחסם.
